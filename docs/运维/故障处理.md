# WYRPlay 故障处理

本文件覆盖当前生产最需要的三类恢复动作：发布回滚、数据库恢复、持久化任务故障。

## 1. 发布故障

生产由 GitHub Actions -> OpenNext Cloudflare -> Cloudflare Workers 发布。

发现发布回归时：

1. 确认影响范围和当前 production commit。
2. 如果继续流量会扩大数据错误，先停止对应写入或后台任务。
3. 使用已知可用的代码版本重新发布；不要盲目倒转数据库 migration。
4. 验证 health/readiness、首页、投票读写、受影响页面和关键安全头。
5. 涉及数据写入时核对数据库状态后再宣布恢复。

若旧代码不能安全运行在新 schema 上，旧 deployment 不是合法回滚目标，应做向前修复或按批准方案恢复数据库。

## 2. 数据库恢复

不要对 production 执行临时 down migration。

需要恢复时：

1. 从批准的 provider backup/PITR 恢复到第二个隔离数据库。
2. 对恢复库执行：

```bash
RESTORED_DATABASE_URL="postgres://..." bun scripts/verify-restored-database.ts
```

3. 确认 migration、关键表和约束完整。
4. 确认恢复点之后有哪些写入需要重放或人工对账。
5. 获得明确批准后再切换流量。

测试数据库 reset 逻辑绝不能指向 production。

## 3. 持久化任务与死信

平台仍保留 durable job / dead-letter 设施。处理死信时：

- 先修复根因；
- 确认条目仍处于可重试的 dead-letter 状态；
- 确认重试受幂等规则保护；
- 使用脱敏 inspection 工具；
- 记录具体 retry reason；
- 不直接改业务结果表来伪造“成功”。

示例：

```bash
APP_ENV=staging DATABASE_URL="$DATABASE_URL"   bun scripts/inspect-dead-letters.ts --environment=staging
```

需要重试时按脚本要求提供 environment、queue、id、reason 和 confirm。

## 4. Kids privacy incident

如果发现 Kids vote 写入了持久化 voter cookie、可复用 child/browser identifier，或把 Kids 行为送入不允许的分析/广告链路：

1. 立即阻止继续写入；
2. 保留最小必要取证，不扩散儿童数据；
3. 确认影响时间窗和字段；
4. 修复并跑 Kids privacy 相关测试；
5. 根据真实影响决定是否需要数据清理和进一步法律/隐私处理。

## 5. 记录

事故记录应包含：

- 时间线；
- 影响范围；
- before/after commit；
- schema/runtime/config change；
- 恢复动作；
- 验证结果；
- 后续措施。

不要在事故记录中粘贴 secret、完整数据库行或不必要个人信息。
